## Findings (structured)

- **MEDIUM-1 (MEDIUM)** `backend/app/lab/agent_history.py`: Replay episodes will enter every later same-agent history as ordinary 'learn_discovery' episodes. The history's frozen SCOPE text calls these "learn campaigns' own discovery picks", and SOURCES describes them as "chosen by the Explorer". After the first live v4 run in a store, any later v3 or v4 plan there will present replay episodes as Explorer or learn picks. Those replay outcomes will also feed the replay rule itself: a replayed row's verified count and share include its own replays. Nothing in that later frozen, hashed plan can tell them apart. The builder disclosed this (docs section 9, CURRENT_STATUS) but did not mitigate it. It does not affect the first live v4 run, because v4 has never run, so no store holds a replay episode. Evidence: agent_history.py lines 41-42 (SOURCES) and 50-54 (SCOPE). _provenance() classifies any episode with study_id == campaign_id == evidence_context_id in a learn campaign as 'learn_discovery'. learning.py runs each replay through runner.run(purpose='discovery') in the same campaign. _public_recipes() also reads replay selection records, because they are challenge False with a selected_output. agent_history.py is unchanged, by the builder's design. Fix: Before creating any v3 or v4 plan in a store that already holds a v4 campaign, do one of two things. Either exclude episodes whose selection record has provenance 'history_replay', or give them their own source label. Both need a new history schema version that saved v3 plans do not use. Until then, add one line to CURRENT_STATUS and the v4 doc: any history frozen after a v4 run must state how many of its learn_discovery episodes were replays, and such rows must not be described as Explorer picks.
- **LOW-2 (LOW)** `frontend/src/components/DiscoveryProtocol.tsx`: The saved-plan replay list labels a replayed row that has no development case '(Explorer pick)'. For example: 'Replay 1 · agent history row 7 (Explorer pick)'. Inside a replay list this reads as if the replay were an Explorer pick, which contradicts the claim rule. It really means the recipe was first chosen by the Explorer in an earlier campaign. It does not show today: the native-v2b list contains only development-case rows. Evidence: DiscoveryProtocol.tsx line 87: row.development_case_id ? ` (${row.development_case_id})` : ' (Explorer pick)'. Fix: Use wording such as '(no development case; recipe from an earlier campaign's Explorer pick)'. Alternatively, drop the parenthesis for rows with no case.
- **LOW-3 (LOW)** `frontend/src/components/RunSummary.tsx`: Some secondary surfaces show a replay-sourced incident without saying it came from a replay. They do not mislabel it; they only omit the label. These are: the Run summary panel's incident stages, the W&B regression dataset rows (experiment_purpose 'discovery'), the Weave traces of the replay's Actor episode, and bundles imported without evidence.json. Someone who sees only those surfaces, for example in a demo, cannot tell a history replay from an Explorer-found source. Evidence: RunSummary.tsx shows 'Latest incident shown' and the Repeat/Simplify stages with no provenance. coordinator.publish_regression_dataset rows carry only experiment_purpose. tracing.trace_metadata has no replay field. The replay label lives in the selection records, the experiments API, the recording and evidence.json only. Fix: When reporting a live v4 result, cite the recording's discovery_history_replays block and the source panel's 'Found by' line, not the Run summary or W&B views. Optionally add a one-line 'Found by: history replay N (row R)' to the Run summary in a later round.
