# Submission evidence checklist

The repository remains private. This implementation does not authorize publication, deployment or hackathon submission.

| Handbook criterion | Reviewable evidence | Acceptance boundary |
|---|---|---|
| Best Loop | Original model proposal, source trials, reduction, tested diagnosis, challenge and fixed promotion result | Pending genuine live generated gain |
| Creativity | Explorer/Mechanic roles, challenge feedback and scoped API evidence-gap experiment | Fixed diagnostic HTTP experiment verified; autonomous findings pending |
| Utility | Exported regression, fresh trusted execution and unchanged policy transfer to an independently authored agent | Runner verified offline; external measurements pending |
| Technical execution | HTTP idempotency, C1–C8, uncertainty, budgets, stop, persistence and repeatable commands | Offline checks; final audit pending |
| Sponsor usage | W&B Inference, verified Weave traces/evaluation/dataset, campaign run and automatic Aria history/output | Adapters; connected acceptance pending |

These are the five names in the supplied handbook, mapped in the reviewed specification's `hackathon-fit.md`. Before submission, the owner must review recorded results, explicitly authorize the handbook's public repository requirement, verify external links, disclose reused scaffold/dependencies and source license, and authorize submission. Never replace missing results with rendered sample data or describe a manual Aria invocation as automatic.
