Discovery protocol v2 applies to this request (discovery_protocol). Where it conflicts with the rules above, this section replaces them.

agent_action_space states the registered agent's real limits and typical behaviour: it has no wait action, every HTTP attempt advances the clock one tick, the adapter retries a failed or timed-out call once, and the agent has at most seven business calls before its final report. It does not send a failed write again: when both attempts of an upgrade or confirmation fail, it checks that operation's status at most three times (a failed check counts) and stops with the task unfinished. normal_path is the agent's call sequence when nothing fails. A fault fires only if its tool/service attempt happens on the agent's path within those limits; a long upgrade delay uses up its calls on status checks.

Before any Actor episode, a free replay of the real simulator labels every fault FORCED, NOT_FORCED or IMPOSSIBLE for this agent (dispatch_rule). Only a recipe whose every fault is FORCED runs. A refused recipe (not all FORCED, or a duplicate) consumes this request and is recorded; the slot then gets exactly one re-plan request, which carries slot_feedback with the refused recipe and a fixed explanation for each fault. On a re-plan, choose a recipe that addresses those reasons. Changing the parameters or count of a fault that was not reached cannot make it reached. An earlier fault in the same recipe can add status checks (an upgrade left pending, or a write that failed on both attempts), but no fault makes this agent re-send a write. So a fault on a third or later attempt of a write is not reached, and after a write fails on both attempts only those few status checks follow: a fault on any later upgrade, confirmation or further status check is not reached. Every F1 delay exceeds the client timeout, so different F1 delays look the same to the agent.

In search_ledger, recipes are written in words. prior_selections and refused_recipes include each fault's label and explanation; tested_schedules include what fired, what did not and why, with attempts counted per tool and service. Primitive order matters only for two faults of the same kind on the same tool/service whose attempts overlap (the simulator uses the first matching F4 or F2 and the last matching F3); otherwise reordering, the seed or the hypothesis does not make a new schedule, and any recipe listed in excluded_recipes is a duplicate.
